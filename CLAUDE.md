## What this directory is

`iyye_2/` is the project area for **Iyye 2.0**, a reimplementation of the Iyye personal assistant on reused upstream foundations. Implementation has started in `host/`: M0–M7 and M3b are done: skeleton, control state and admission, local model management, the locked-down Pi integration, read-only tools, the owner web chat, Telegram receiving (poller) and sending (outbox), the scheduler (fair ordering, leases), trust commands, and the §9 acceptance suite (`test/acceptance.test.ts`, mapped in plan M7). M8 (real use) closed on 2026-10-07 after six days (`host/NOTES-0.001.md`): 0.001 is complete. Long-term memory (0.002) is planned in `iyye_2_0_002_plan.md`: Hindsight behind Iyye's scoped memory gateway. Its L0 spike is done (`memory/SPIKE.md`); `memory/` holds the Hindsight venv (`memory/.venv`, 0.10.2, the live one on the Spark, a dev venv on the Mac; its Spark list `memory/requirements-linux-aarch64-0.10.2.lock`) and Iyye's PostgreSQL + pgvector (`memory/pg`, conda-forge, pinned by `memory/pg.lock`, on the Spark `memory/pg-linux-aarch64.lock`); both are untracked. Hindsight 1.2.0 is prepared (2026-11-06, `memory/UPGRADE-1.2.0.md`: rehearsal on a copy of the live data, smokes, the owner's runbook and rollback): installed on the Spark in its own directory `iyye_2/memory-1.2.0` (`.venv`, `pg` a link to `../memory/pg`; lists `memory/requirements.lock` and `memory/requirements-linux-aarch64.lock`), selected with `IYYE2_MEMORY_DIR`; the switch is the owner's, and its migrations cannot be undone (the way back is a copy of `pgdata`); `MemoryService` refuses to start a Hindsight older than the newest one recorded in `<state>/memory/hindsight_version`, since 0.10.2 would run on 1.2.0's database without a word. dateparser is held at 1.4.3 (1.5.0 breaks Hindsight's date analysis). 1.2.0's consolidation re-asks every fact left unplaced, Iyye's own capped-at-0 facts included (the heaviest live night: 176 s → 630 s), so the night waits up to 1,800 s for it. L1 is built: `host/src/memory/` (`postgres.ts`, `service.ts`) supervises them via the shared `host/src/process/supervised.ts`, which the router uses too; `host/scripts/provision-memory.ts` downloads the local models once (the host never goes online for them); `host/scripts/memory-smoke.ts <scratch>` is the real-service smoke. L2 is built: Hindsight's model calls go only to the host's lease-gated pass-through (`memory/passthrough.ts`, 503 unless admitted), and memory work gets the device only through `MemoryGate.run` (`memory/gate.ts`), which shares one `DeviceSlot` (`kernel/device.ts`) with chat jobs and console turns and never waits in line ahead of chat; the memory model is selected with `/use <model> memory`. Memory follows 1.x's **day/night** split (plan §3.4, HLD §6.1). During the day, turns recall from STM, which is today's answered turns in SQLite (`state/stm.ts`, FTS5, written in the outbox's answered transaction), and from LTM (Hindsight recall, which makes no model call). Both go through the scoped `memory/gateway.ts`, a request-local Pi `context` hook, and the `memory_search` tool. Recall rewrites the question for the reader (`memoryQuery`: "I"/"we" → "the user" or the contact's name; stated relations add names) and merges banks by Hindsight's reranker score: the reader's own bank always contributes, a person the question names contributes, other banks only strong matches; one failing bank drops only itself. Nothing generative runs while Iyye is awake. At night, `kernel/rhythm.ts` sleeps on the rest window (`IYYE2_SLEEP_WINDOW`), on catch-up, or on `/sleep`; contacts wait, and owner input wakes Iyye. When a night completes, every conversation's Pi session is retired (`PiConversations.resetAll`), so chat history lasts one day and continuity comes from memory (owner decision). STM is today only: at the end of a completed night `endDay` moves anything unstored to a bounded, never-recalled transfer backlog (3 attempts or 7 days, then dropped and reported). Asleep, every model except the memory model is unloaded, and waking loads the chat models again (`ModelManager.restForNight` and `wakeFromNight`). `memory/night.ts` retains each STM episode through the gate (reasoning on), consolidates (reasoning off), and clears STM. What it keeps (2026-10-06): people's words (extracted under `RETAIN_MISSION`); Iyye's replies not verbatim but extracted as dated "Iyye told <person> that …" facts (strategy `iyye-reply`, `REPLY_MISSION`, tagged `speaker:iyye`); Iyye's own durable entries only (self-model changes, repository findings, investigation answers; machine findings and day summaries stay in STM). Consolidation never builds observations from `speaker:iyye`/`speaker:probe` facts (a tag-matched Hindsight consolidation strategy with a cap of 0), people's banks have an observations mission, and `iyye-self` builds none. `host/scripts/memory-night-smoke.ts` is the real night smoke. For debugging, `node scripts/dump-ltm.ts [--bank <id>] [--type world|experience|observation] [--q <text>] [--limit <n>] [--json]` prints every memory Hindsight holds, bank by bank (read-only, no model call, works awake or asleep), and `node scripts/memory-clear.ts [--bank <id>] [--restage] [--yes]` deletes the live Hindsight banks (everything in them; it cannot be undone). `--restage` puts the conversations already moved back into STM, so the next `/sleep` re-runs the night on them. ## Host commands (`host/`)

- `cd host && npm test` runs every test. Run one file with `node --test test/admission.test.ts`.
- `npm run check` runs biome with `--write`, so it reformats files, then `tsc --noEmit`.
- There is no build step. Node runs `.ts` directly by stripping types, so:
  - relative imports need `.ts` extensions,
  - type-only imports need `import type`,
  - only erasable TS syntax works: no `enum`, no parameter properties.
- Dependencies are pinned exactly and listed in `host/PINS.md`. Install with `npm install --save-exact --ignore-scripts`.
- New 2.0 TS and SQL files start with the short header `Copyright 2026 Alexander Komarov` + `SPDX-License-Identifier: Apache-2.0`.
- Schema changes go in a new numbered file in `host/src/state/migrations/`. Never edit an applied migration.
- Run the host with `cd host && node src/main.ts`. Configuration comes from `IYYE2_*` environment variables (plan §6), and state lives in `~/.iyye2`. It starts its own llama.cpp router on `127.0.0.1:8180` (every model with `--load-mode` from `IYYE2_LLAMA_LOAD_MODE`, default `none` on Linux, where CPU and GPU share memory, and llama.cpp's own default on macOS), loads `IYYE2_DEFAULT_MODEL`, and serves the owner web chat on `127.0.0.1:5100`. `IYYE2_WEB_LISTEN` (owner decision 2026-10-09) can put it on the LAN (`0.0.0.0` or one address). It is still token-authenticated, but plain HTTP, so the session cookie crosses the LAN. Host and Origin may then also name the address a request arrived on or the machine's hostname, and any other name is refused (DNS rebinding). The login URL `/login#<token>` is printed at startup; the token is in `~/.iyye2/owner_token`. On a terminal it accepts the owner commands (`/models`, `/load`, `/unload`, `/use`, `/router restart`, `/contacts`, `/trust`, `/untrust`, `/day`, `/night`, `/memory`, `/sleep`, `/wake`, `/focus`, `/pause initiative`, `/resume initiative`, and the rest listed by `/help`; the same set works in the web chat), and any other line is a chat turn in the dev-only `owner-console` scope.
- Every outward message goes through the outbox (never write to `web_feed` or call a channel API directly): `Outbox.deliver` for replies, whose route comes from the triggering event; `Outbox.sendOwn` for Iyye's own messages on an exact route (reminders, with `commitment_id`; messages sent for the owner, key `notice:send:<id>`), and its case `notifyOwner` (the owner's web chat). Web tests use raw `node:http` (`test/web-helpers.ts`), because fetch rewrites Host/Origin.
- Telegram tests use the in-process fake Bot API `test/fixtures/fake-telegram.ts` (per-chat scripted ok/429/400/403/500/hang/drop for sendMessage; long-polling `getUpdates` with offset semantics via `receive()`; scripted `getMe`/`getUpdates` failures). Never send to the real Telegram API from tests or probes. A channel adapter returns ok:false only for a definite non-delivery and throws when the message may have gone out; never log the bot token.
- Model and Pi tests use the fake router `test/fixtures/fake-llama-server.mjs`, never the real binary. It streams OpenAI-style chat replies scripted by markers such as `[[empty]]`, `[[fail]]`, `[[slow]]` and `[[history]]`.
- A new tool is an `IyyeTool` in a **toolkit** registered with the `ToolBroker` in `main.ts` (plan 0.004 T1). A toolkit's `effect` decides who gets it: `read` toolkits are for everyone, owner and contacts (owner decision); `self` (reminders, plans) reaches only the asker's own route; `reach` (`messaging`, plan 0.008) is for the owner, trusted contacts and Iyye's background work (owner decision); `act` toolkits (today `thinking`) are for the owner and trusted contacts: trust alone, no per-toolkit grant (owner decision 2026-10-19); `private` (read-only, but the owner's: the `project` toolkit, Iyye's own repositories) is for the owner and Iyye's own work, never contacts. Since 2026-10-08 the owner's turns get `project` (declared last): `git_log`, `git_show`, `git_status`, `read_file` and `list_dir`, confined to the repository. `IYYE2_PROJECT_REPO` defaults to the iyye_2 repository (`0` turns it off), and an absolute path from another machine that names the repository's folder is read as the same path here. Toolkits and tools are declared in one fixed order, because any change to the declared set makes llama.cpp reprocess the whole conversation; with acting toolkit selection a session's added toolkits follow the order they were added in (Pi 1.5 appends newly active tools and never moves the earlier ones), and that order never changes within the session. Never give a session tools any other way, and never expose a shell or interpreter to it, except the sandbox (owner decision 2026-10-12): `sandbox_run` (`tools/sandbox.ts`, effect `compute`: the owner and Iyye's own work, never contacts or plan steps; `evidence: false`, so `tool_calls.result` keeps only a fixed note and no citation check can use its output) runs `/bin/sh -c` in a rootless runc container built only by `sandbox/config.ts` (its own network namespace, read-only pinned Alpine + python3 root, only the scope's `/work`, no capabilities, a fixed env; `assertIsolated` refuses anything else) with memory and task limits on the container's own cgroup (runc creates it in the delegated systemd user tree its `systemd-run --user --scope` provides; a scope's own limits do not reach the container) and a wall-clock kill; CPU is bounded only by the wall clock (`sandbox/sandbox.ts`); `/work` is wiped at the end of a completed night and on `/forget`. Provision with `node scripts/provision-sandbox.ts` (the only configuration with the host's network); `node scripts/sandbox-smoke.ts <scratch>` is the real smoke. Tests use a fake runc; never run the real one from a test. `IYYE2_SANDBOX=0` turns it off; `IYYE2_SANDBOX_BACKGROUND=1` gives it to Iyye's own work (a new M4 trial period). The `monitor` toolkit (`tools/monitor.ts`, owner decision 2026-10-12, effect `private`, plan 0.004 §10) gives the owner's turns typed host readings: `gpu_status`, `temperatures`, `pressure`, `top_processes` (program names only, never command lines), `io_rates`, `system_errors` (secrets masked); Iyye's own work only with `IYYE2_MONITOR_BACKGROUND=1`. Tools that need arguments must not let the model widen what they reach.
- Turn guards (2026-10-05 runaway turn: 125 validation-rejected `web_search` calls in 1.5 h): every tool result counts toward a turn-level guard (`ToolLoopGuard` in `integration/pi/turn.ts`: 12 results, or the same failure 3 times in a row, then one recovery step with tools closed and thinking off); tool arguments are shortened (`shorten`), never limited by schema `maxLength`; `enable_thinking` follows the session thinking level (`thinkingLevelFor`), and compaction runs with thinking off; device time costs at most `devicePerTurnMax` energy per turn.
- Model self-healing (2026-10-05 incident: a wake-time load failed while the Mac slept, and chat failed all morning): by day, a model selected for a chat channel or background work that is not loaded is loaded again with backoff (`healBackoffMs`, then Iyye gives up and says so); a job asking for it gets a `busy` refusal and waits; a model the owner unloaded by hand is left alone until waking or `/load`; nothing is reloaded at night. Load and unload deadlines use `AwakeStopwatch` (awake time), because Node's monotonic clock counts system sleep on macOS.
- Unhandled rejections crash the host (2026-10-21, twice: the thinking model's health check did `return this.checkOpenAi()` inside `try` without `await`, so a `socket hang up` on `/v1/models` escaped the `catch` into a timer callback). Inside `try`, always `return await` a promise. Node prints an unhandled rejection as the error's own stack with no `Unhandled 'error' event` line; that line means an emitter with no `'error'` listener. `process/client-requests.ts` is the backstop for the second kind: every client request gets an extra `'error'` listener at creation (`diagnostics_channel` `http.client.request.created`), so a request nobody else listens to becomes a warning naming the line that created it. Every request must still handle its own errors.
- Owner directive: a slow answer beats a timed-out one. The chat path has no model-time limits (Pi `httpIdleTimeoutMs: 0`, router `--timeout 86400`, preset `timeout = 86400`); never add one. Thinking is a per-model registry key (`thinking: on|off`, sent explicitly as `enable_thinking`), and each request carries an explicit `max_tokens`.
- Every Pi session must be built through `PiConversations` (`integration/pi/sessions.ts`). A bare `createAgentSession()` reads `~/.pi`, discovers AGENTS.md/CLAUDE.md and extensions, enables bash/edit/write, and can reach hosted providers. Real-router behaviour the code relies on is recorded in `host/PINS.md`. Before switching llama.cpp builds, run `node scripts/probe-router.ts <llama-server> --tools gemma-4-E4B` (it uses its own free port and an empty cache), compare the result with `PINS.md`, then update `IYYE2_LLAMA_SERVER`'s default in `config.ts`.

## Architecture of 2.0 (HLD summary; read the HLD before designing)

- **Foundation chosen by the owner:** Pi + a custom self-hosted Hindsight integration + local Kev-like decision models. Hermes is the documented alternative but must not be implemented in parallel (§2.2). Re-opening this choice requires an owner decision.
- **Fork discipline (§2.3):** keep upstream code recognizable. Iyye code lives in its own package and uses supported extension points. Keep any Pi core patch to a minimum, document it, and back it with a conformance test showing that no supported boundary works.
- **Layout (§12.1):** `host/src/{kernel,state,character,memory,decisions,tools,integration/pi,channels}` is the TypeScript resident host. So far: `state/`, `kernel/{admission,commands}.ts`, `models/` (registry, preset INI, router process, router client, memory probe, manager), `integration/pi/` (local-only runtime, resource loader, prompt, per-scope sessions, turn runner), `tools/` (broker, read-only probes, `memory_search`), `outbox/` (transactional outbox, message splitter), `channels/telegram/{poller,sender}.ts` (Telegram receiving and delivery), `kernel/{scheduler,recovery,device,rhythm}.ts`, `memory/` (PostgreSQL and Hindsight supervision, pass-through, gate, gateway, night, report), `state/stm.ts`, `process/supervised.ts`, `channels/web/` (authenticated web chat server, delivery adapter, static UI in `ui/`), `channels/types.ts`, `config.ts` and `main.ts`. `config/identity.md` is the identity prompt. The model registry is `config/models.json`. `decision-worker/` is the Python Kev adapter and trainer. `evals/` and `config/` sit alongside. Model artifacts, datasets, secrets, and live state stay out of source control.
- **Separation of authority (§3):** Pi owns turns, tools, compaction, and cancellation. The **behavior kernel** (deterministic, event-driven) owns admission, focus, modes, budgets, plans, commitments, and permissions. The **memory service** only supplies evidence. The **decision service** only supplies typed probabilities. Neither memory nor a classifier can grant permissions, change identity, fabricate a receipt, or commit control state.
- **Control state lives in SQLite (§3.1):** events, jobs, plans, commitments, actions, receipts, contacts, character revisions, memory transfers, decisions, training examples, and model revisions. It is not a second vector store. Semantic memory lives in Hindsight, and transcripts live in Pi's session store.
- **Effects go through a transactional outbox (§7.3):** every outward reply, including Pi's normal final answer, goes through it. Routes are exact, with no cross-channel fallback. A send that may have happened without confirmation is recorded as `unknown`, never blindly retried. A commitment is fulfilled only by a matching receipt plus acceptance evidence.
- **Scoped memory gateway (§6.2–6.3)** is the only path to Hindsight. Banks and scope come from the authenticated event, never from the model. No model-reachable worker holds an unscoped client.
- **Typed decisions (§9.4):** finite candidate sets, schema validation, abstention bands, and a deterministic fallback for every role. Every decision is logged with its model/adapter/head/calibration revision.
- **Local-only by default:** hosted inference is never an automatic fallback.

## Invariants carried over from 1.x (must not be weakened)

- Telegram is untrusted. Only an authenticated local owner operation can bind identities, change grants or trust, or approve plans that widen what Iyye may do. Remote PINs, quoted owner requests, and already-trusted contacts cannot delegate any of that. The one owner-made exception (plan 0.005, owner decision): a Telegram account the owner linked with `/link <account> owner` *is* the owner in dialogue, memory and tools. Commands from it are still plain dialogue; owner commands work only from the web chat and terminal. Every principal is decided by `resolvePerson` (account → person) at admission; never derive scope another way.
- Autonomous jobs get typed read-only probes, never unrestricted Python or shell gated by a regex. The one effect they have is `telegram_send` (plan 0.008, owner decision): labelled, capped, and reported to the owner. The one place code runs is the sandbox (owner decision 2026-10-12), an isolated container with no network and no host access beyond its own `/work`, never on the host itself; its output is never evidence.
- A self-authored reflection or narration never counts as an outcome or as evidence for more work. Learned mechanisms are bounded, damped, reversible, and credited to the author or action that caused the outcome (§11.2).
